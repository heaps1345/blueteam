Stage 1 — Local Linux Analysis
01

Hashing and file identification

Always hash before anything else. The hash is what you'll search against VirusTotal, and it's your proof that the file didn't change across every later step.

$sha256sum beacon.exe
Produces a unique fingerprint of the exact file contents. This is the value you paste into VirusTotal's search bar — VT indexes by hash, not filename, so two people calling their file something different will still match if the bytes are identical.
saved
$file beacon.exe
Confirms the file format by checking the actual header bytes rather than trusting the file extension. For a PE binary it'll report the architecture (x86 vs x64), whether it's a GUI or console app, and whether it's statically or dynamically linked.
saved
$exiftool beacon.exe
Pulls any embedded metadata — compile timestamp, version info, company/product strings. For generated payloads this is frequently sparse or absent, which is itself a finding worth recording rather than skipping.
saved
02

Strings and embedded indicators

Windows binaries store a lot of text as UTF-16LE (wide chars), which plain strings misses by default. Run both passes.

$strings beacon.exe | less
Extracts printable ASCII sequences. Look for DLL names, function names if unencoded, and anything resembling a URL, IP, or port — even partial fragments can be telling.
$strings -el beacon.exe | less
The -el flag extracts little-endian wide-character (UTF-16LE) strings — the encoding most native Windows API text actually uses. Skipping this pass is the single most common reason students think a binary has "no strings."

03

Static structure — sections, imports, entropy

This is where peframe earns its place — it automates most of what you'd otherwise do by hand across several tools.

$peframe beacon.exe
Reports sections with entropy, suspicious imported API calls, packer signatures, and any obvious indicators in one pass. Treat its "suspicious" flags as a checklist to verify manually, not a verdict on their own.
saved
saved
$objdump -p beacon.exe | grep -A50 "DLL Name"
A no-extra-install way to dump the import table directly. Cross-check this against peframe's flagged list — seeing it from two angles helps you trust the finding.
saved
$binwalk -E beacon.exe
Renders an entropy graph across the whole file. A flat low region followed by a sharp spike close to the maximum is the visual signature of encoded/compressed payload content sitting inside an otherwise normal-looking executable.

Stage 2 — VirusTotal
04

Submitting the hash, not the file

Always search by hash first. Uploading the actual file is sometimes unnecessary and means the sample becomes visible to every VT customer afterward — worth knowing before you do it with anything sensitive.

1Go to virustotal.com and paste your SHA256 hash into the search bar.
2If it returns "no matches found," that just means nobody has submitted this exact binary before — for a freshly self-generated lab sample with unique build artifacts, this is expected and not unusual.
3If you want a result for class purposes, you can upload the file directly — only do this with lab-only samples you're comfortable becoming visible on a shared threat intelligence platform.
4Once scanned, note the detection ratio (e.g. "34/72") and look at the Details tab for file type, size, and any TRiD/packer identification.
5Check the Community and vendor name columns under Detection — compare how different engines label it.
Before uploading anything: confirm with your instructor/institution's policy on submitting samples to third-party platforms, even self-generated ones — some training environments restrict this.

Generic detection names

Names like "Trojan.Generic" or "Gen:Variant.Heur" usually mean a vendor's heuristic/behavioral engine flagged a pattern — not that they identified the specific framework. Worth contrasting with named-family hits.

Named-family detections

Hits explicitly naming Meterpreter, MSF, or similar mean a vendor has a signature tuned to this exact framework's known stub/structure — common since msfvenom's default templates are extremely well fingerprinted.

Low detection ratio

A surprisingly low ratio doesn't mean "safe" — it can mean the sample is new/unique enough that signature-based engines haven't matched it yet, which is a good discussion point about the limits of static signature detection.

Stage 3 — Joe Sandbox
05

Behavioral analysis in a sandbox

This is where you finally watch the sample run, in an environment built to observe and contain it. Joe Sandbox's free Cloud Basic tier is generally sufficient for a teaching sample.

1Go to joesandbox.com and create or sign into an account.
2Choose a Windows analysis environment matching your sample's architecture (x86/x64), and submit the file for analysis.
3Once the run completes, open the Behavior Graph first — it visualizes process creation, file writes, and registry activity as a tree, which is the fastest way to get oriented.
4Check the Network Behavior tab for any outbound connection attempts — since your LHOST is non-routable, expect a failed/timeout connection attempt rather than a live callback, which is itself worth noting as expected lab behavior.
5Review the Signatures tab — Joe Sandbox tags specific behaviors (e.g. "starts servers," "may sleep to evade dynamic analysis," "reads sensitive process memory") with severity scores.
6Note the overall threat score and compare it against what static analysis already suggested — did dynamic analysis confirm, add to, or contradict your static findings?
